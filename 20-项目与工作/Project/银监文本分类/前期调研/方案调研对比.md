

方案 A：混合检索 + 强语义重排 (Hybrid Search + Reranker)

第一步（粗排）： 同时使用 BM25（关键词检索） 和 Vector（语义检索）。关键词能抓住特殊的编号、日期、专有名词；向量能抓住大致含义。
第二步（精排 - 关键）： 使用 Cross-Encoder 重排模型（如 BGE-Reranker）。
原理： 向量检索是计算两个向量的余弦相似度；而重排模型是将“报告片段”和“原始文档片段”同时输入大模型，让模型深度判断两者是否存在因果或支撑关系。这一步是真正的语义理解。

方案 B：知识图谱溯源 (Knowledge Graph RAG)
如果巡检报告涉及复杂的实体关系（例如：某机构-某时间-某违规项）。
思路： 将原始文档和历史报告都提取为 (主体)-(行为)-(结果) 的三元组。
优点： 溯源不再是找“相似的文字”，而是找“匹配的事实”。


方案 B拓展 — 知识图谱 + 向量混合（推荐用于归纳类）
这个方案专门解决最难的场景：一条报告结论是从多份文件归纳出来的，比如"三家单位均存在档案管理问题"，这条结论涉及三个文件，向量检索根本找不出来这种多对一关系。
做法是在数据摄入阶段，用大模型从每份巡查文件中抽取结构化三元组，比如（某单位 → 存在问题 → 档案管理），构建知识图谱，溯源时在图谱上做路径查询而不是相似度检索。技术上可以用 Neo4j 或者 Nebula Graph。



方案 C：基于 Agent 的递归拆解 (Decomposition Agent)
针对那些“一句话总结了十个问题”的复杂报告结论。
思路： 
1.  拆解： 使用 Agent 将报告的一句结论拆解成 N 个“原子事实”。
2.  并发检索： 对每个原子事实去向量库/数据库执行检索。
3.  验证（Reflect）： Agent 获取候选片段后，再次对比：“这段原文是否足以支撑报告中的这个观点？”




历史报告最大的根本困难
不管用哪个方案，有三类情况很可能无解：

第一种是跨文件归纳，结论来自对多份文件的综合判断，没有单一来源。
第二种是编写者的隐性知识，报告结论里夹杂了编写者自己的业务经验判断，这部分在任何文件里都找不到依据。
第三种是语言转换太大，原文是事实描述，报告是政策语言，词汇几乎没有重叠。


### 知识图谱方案

知识图谱,由 实体 和 关系构成, 对应图数据库中的 点 和边 
实际 执行的时候 以三元组的方式, 即 (主体)-(行为)-(结果)

实际执行的时候需要

1. 本体建模 (Ontology Modeling)首先，你需要定义这套业务的“骨架”。
	实体（Nodes）：定义什么是“巡查对象”、“问题类别”、“法律法规”、“时间”、“底稿条目”。
	关系（Edges）：定义它们之间的连接方式。例如：[底稿 A] —— 属于 —— [履职风险类]；[底稿 A] —— 违反了 —— [管理办法第X条]。
2. 知识抽取 (Knowledge Extraction)这是最难的一步，需要把非结构化的 Word 变成结构化的三元组。
	1. NER（实体识别）：利用模型识别出底稿里的所有公司名、人名、法规名。
	2. RE（关系抽取）：识别出这些实体之间的逻辑。例如从“某分行未按规定进行双人核对”中抽取出 (某分行, 违规行为, 双人核对)。
3. 实体统一与对齐 (Entity Linking)将报告和底稿中表述不一致的词指向同一个节点。
	比如报告写“银保监”，底稿写“监管部门”，图谱需要通过别名表或向量相似度把它们合成为同一个实体节点。
4. 路径检索 (Graph Traversal / Reasoning)当输入一段报告文字时：提取报告中的关键实体。在图谱中寻找这些实体与哪些“底稿片段”节点有共同的关联路径。通过路径的权重计算得出最可能的溯源结果。

不适合的原因

1. 语义的“非结构化” 导致标准的实体抽取困难,而准确性严重依赖抽取的精度
2. 要大量的梳理,定义的工作(哪些是实体,关系有哪些(- 关系类型多少种？“违反”“属于”“发生在”“涉及”“引用”……每增加一种关系，抽取模型的复杂度就上升一个数量级。))
3. 僵化,业务逻辑的改动, 书写方式的改变都将导致 失效



可解释性强,可以输出完整的溯源链
	如 报告中的“贷前调查不严” → 匹配到底稿A中的“客户经理未实地走访” → 该底稿关联的法规是《XX办法》第12条 → 该法规同时出现在另一份报告的问题清单中。
