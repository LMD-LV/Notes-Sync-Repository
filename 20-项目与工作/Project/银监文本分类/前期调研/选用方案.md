### 技术栈

智能断句器(将句子拆分成为断句,同时自动提炼实体)+Embedding向量检索 + (BM25)混合检索+ 跨文档语义聚类(将不同的底稿智能分类) + 不同分组自动标签 + 支持(组/段落 结合的搜索方式) +Reranker精排 + 置信度标记

### 完整技术层级描述

L1 数据接入层
将原始Word底稿解析为结构化的条目级文本片段。
区别于简单的全文提取，本层使用智能断句算法，智能匹配常见列举结构（如“一 是……二是……”），将一份底稿中混合的多个条目拆分为独立单元。
同时，自动识别并提取底稿中的主体（人名、机构名称等）、时间、数值等标签，使得切片更加精细化，保证词义切割的准确性。
智能断句算法中的主题识别，支持手动维护行业场景的主题名称，保证缩写匹配的场景。
技术上使用 python-docx 完成文档读取，配合自定义规则和智能算法完成条目级拆分。
亮点：切片粒度细化至条目级，并附加实体标签，从源头保证语义纯净和元数据丰富。


L2 向量构建层
将清洗后的底稿片段双路入库，同时建立向量索引和关键词索引。
这一层做了两件独立的事。
第一路，使用 BAAI/bge-m3 模型将每个片段转为高维向量，写入 Chroma 的 chunks 集合，用于后续的语义相似度召回。
第二路，同步构建 BM25 倒排索引（rank_bm25），专门应对报告中出现的机构编号、法规条款编号、具体数值等精确匹配场景。两路索引并行存在，分别服务于不同类型的查询。
亮点：双路索引设计，语义检索与精确匹配各司其职，避免单一检索通道的盲区。


L3 聚类标注层
对所有底稿片段做跨文档语义聚类，生成主题簇，并为每个主题生成业务语义标签。
使用 BERTopic + HDBSCAN 对全量片段进行密度聚类，自动识别“履职监管”“整改落实”“风险排查”等跨文档的主题簇，每个簇包含 centroid 向量、c-TF-IDF 关键词和成员片段列表，整体写入 Chroma 的 topics 集合。
在此基础上，使用 Qwen2.5-1.5B 对每个主题簇做自然语言标签生成，将机器聚类结果转化为可读的业务语言；同时支持业务补充不同的主题名称，对应不同的巡查场景，并为每份底稿写入元数据，为后续检索提供过滤依据。
亮点：增加了跨文档的词义理解能力，显著提升了对模糊数据的识别能力。


L4 报告解析层
对输入的历史手写报告进行分句和内容分类，为后续多通道检索提供路由依据。
报告段落往往一段话同时涉及多个底稿来源，如果以段落为单位检索，会导致召回结果混乱。本层首先使用智能断句算法（与 L1 类似），将报告拆分至句子级；随后使用智能内容分类算法，对每个句子进行内容类型识别并区分以下四类：
事件类：描述行为、问题、过程的陈述句
实体类：涉及机构名称、人名、文件编号等命名实体
总结类：如“总结上述情况”“可得结论”“综上所述”等元内容（非底稿原始信息）
数值类：包含百分比、金额、数量等可量化内容（作为补充类型保留）
数值类由正则规则识别，实体类由 NER 模型处理，事件类和总结类由语义模型结合上下文判断。
亮点：智能断句算法 + 智能内容分类算法双重处理，从源头保证每个检索单元语义单一，避免总结类内容污染后续检索。


L5 多通道检索层
根据 L4 的分类结果，将不同类型的句子路由到最合适的检索通道，分别召回候选片段。三条通道并行运行。
数值类：走 BM25 关键词检索，利用倒排索引精确匹配编号和数字，避免语义向量对数值不敏感的问题。
事件类：走双层向量检索——先在 topics 集合中匹配最相关的主题簇，再在 chunks 集合中做片段级语义召回；双层结果并列输出，并通过向量相似度自动验证主题与底稿片段的对应关系，互相校验后输出。
实体类：通过 NER 识别出机构名称后，直接在底稿元数据中过滤，缩小检索范围后再做语义召回。
总结类：路由至事件类通道，同时提升主题簇权重，增强跨文档归纳能力。
亮点：混合检索（BM25 精确匹配 + 双层向量语义检索），各通道各司其职，同时通过双层向量自动验证机制显著降低主题-片段错配风险。


L6 精排层
将多通道的候选结果合并，统一送入 Cross-Encoder 模型做二次精排，输出 Top3 最终候选。
Embedding 模型在召回阶段使用的是“双塔”结构——报告句子和底稿片段分别编码为向量后计算相似度，速度快但精度有限。Reranker（bge-reranker-v2-m3）使用 Cross-Encoder 结构，将报告句子和候选片段拼接后一起输入模型，能捕捉到两段文本之间更细粒度的语义关联，显著提升排序精度。
精排阶段处理的候选数量已经由 L5 压缩至约 10~15 条，计算量可控，在 CPU 上单次精排耗时约 1~3 秒。


L7 结果输出层
对精排结果按置信度分级，输出可供人工审核和导出的溯源结论。
结果分为三档（置信度阈值支持动态配置，可根据客户对精确度优先或召回率优先的需求进行调整）：
高置信度（默认 ≥ 0.85，可调）：精确度优先，直接标注来源文件名和对应段落，可直接使用。系统保证该档输出精确度最高。
中置信度（0.6~0.85，可调）：输出候选列表，进入人工审核队列，由审核人从候选中确认正确来源后写入最终结果。
低置信度（< 0.6，可调）：标记为“跨文件归纳”或“无法溯源”，说明该结论可能来自多份底稿的综合判断或编写者的隐性经验，系统诚实地标记而非强行给出错误来源。
亮点：分级输出 + 阈值动态配置机制，在人机协作中实现精确度与召回率的灵活平衡，高置信度结果始终保证高精确度。


### 整体技术架构升级亮点：

检索层：向量（BGE-M3）+ 关键词（BM25）混合检索 + Reranker 精排。
分块粒度：底稿按「一是/二是」条目拆分，报告按句子拆分。
智能分类：报告段落自动识别类型，走差异化检索通道。
自动标签：利用聚类结果 + LLM 为底稿/主题打语义标签和风险等级。

双层检索引擎环节（Core Retrieval Engine）

主题层：
查询向量 vs 所有主题 centroids → Top5（余弦相似度）
可选：主题约束模式（只在 Top1 主题成员片段内检索）

片段层（混合检索）：
BGE-M3 向量检索 Top9
rank_bm25 关键词检索 Top9
融合得分：score = α * vector_score + (1-α) * bm25_score（α=0.7 默认）
bge-reranker-v2-m3 精排 → Top3




切片时，每个 chunk 必须附带结构化元数据一起存入向量库，包括：巡查时间、被查机构名称、问题类型/严重等级、文件来源。否则你说的"按时间范围过滤"根本无法实现——纯向量相似度搜不到"2023年的问题"这类语义。

机构名称、法规编号这类关键词靠向量语义相似度往往召回偏差，建议向量检索 + 关键词检索（BM25）结合，再加 Rerank 模型重排精选前 N 条，这样召回质量会稳定很多。

建立“依据索引库”：
巡检依据是相对固定的。建议先花精力把依据库做成结构化的知识图谱或带元数据的向量库。
不要漏掉“硬规则”：
很多手写报告里会有固定的条款编号（如：违反了第 2.1 条）。对于这种信息，直接用正则表达式提取，比任何大模型都好使。

切片优化： 在将原始巡检文件入库时，不仅存 MD 片段，还要存元数据（文件名、页码、巡检时间、被检查机构）。
双向召回： 搜索时，先用报告里的关键词（如机构名、日期）做硬过滤，缩小范围，再跑向量相似度。


### 为什么有了BM25还是使用实体识别

BM25 的本质：

它就是一个经典的倒排索引 + TF-IDF 变种打分公式。
L2 阶段一次性对所有 chunk 做分词，构建这个索引。
查询时直接调用 bm25.get_scores(query_tokens) 得到相关性分数。
它不依赖向量，是纯文本统计的精确匹配方式，和向量检索完全互补。

所以系统里是双索引并存：
Chroma（向量 + 元数据）
BM25（独立的关键词倒排索引）

为什么实体类不用 BM25，而是用元数据过滤？

因为实体类有更高效、更精确的处理方式：

实体通常是结构化的（机构全称、简称、人名、文件编号等），L1 已经通过 NER + 规则提前提取出来，存成了独立的 metadata 字段。
元数据过滤 是精确匹配 + 索引级加速（Chroma 内部对 metadata 做了索引），速度极快，几乎 0 延迟。
BM25 是全文关键词搜索，虽然也能搜到实体，但：
容易受分词噪音干扰（例如“XX监督管理局”可能被拆成多个 token）。
无法利用 L1 已经提取好的结构化信息。
在海量 chunk 中直接 BM25 搜索实体，召回会带很多无关结果，效率不如先 metadata 过滤再向量召回。

元数据过滤 = 利用 L1 提前结构化好的字段，在 Chroma 里做精准、高效的范围缩小；BM25 则是给“无法提前结构化”的场景（纯编号、金额、条款等）准备的精确关键词通道。


为什么要做两个库（而不是只存 chunks）？

Chroma chunks：粒度细，适合精确的片段级检索（L5 第二层召回）。
Chroma topics：粒度粗，把跨文档的“同类主题”先聚在一起，能让系统在处理总结类、归纳类语句时先找到“这是哪一类问题”，再精准落到具体底稿片段，避免在几十万片段里瞎搜。


### 当前方案的缺点

无法处理以下的问题

1. **编写者隐性知识**：报告中夹杂编写者的经验判断
2. **跨文档数据计算**：报告中引用的统计数据来自汇总计算
3. **语言转换过大**：底稿是事实描述，报告是政策语言
4. **V2 特有：聚类漂移**：新底稿主题分布差异大时，簇结构失效



### 缺陷场景的解决思路

对于第二点,有以下思路
- 硬编码计算逻辑
- LLM + 工具调用(工具自己写,或者定义好业务计算逻辑)
- 交互流程优化: 识别出涉及数值计算之后,将可能的数据反馈给用户来标注

对于第一点,第三点
 - 维护专业词词典,对于缩写的词语清洗的时候自动化转化


模糊数据（尤其是经过作者大量语言转化、归纳总结、提炼结论的部分），确实是溯源任务中最具挑战性的场景。纯语义匹配在这里往往表现不佳，因为报告句子与底稿原文的语义距离可能很大（paraphrasing、抽象化、跨文档综合等）。

优化: 
	L4 的智能内容分类算法 是关键第一步：它把总结类句子单独识别出来（“综上所述”“可得结论”等），不再让它们污染普通事件类的检索。这一点非常重要，很多通用 RAG 直接把总结句当作普通 query 处理，导致召回噪声极大
	L5 的双层向量检索（topics → chunks） + 自动验证机制  先在**主题簇**层面做粗召回，能捕捉跨文档的归纳性内容（比如多个底稿里零散的风险点，被报告总结成一句话）。 再落到具体片段，并通过向量相似度**自动验证**对应关系，减少错配。 这比单一向量召回（通用方案常见做法）更适合总结/归纳场景。
	L3 的跨文档聚类 + 业务标签生成（支持手动维护）：让系统提前把“同类问题”聚在一 起，增强了对模糊、分布式信息的理解能力。


L1 中的智能断句算法不仅完成条目级切分，还通过命名实体识别（NER）和规则结合，自动提取主体、时间、数值等结构化标签，并对句子进行初步类型判断。这些结构化元数据被存入 Chroma chunks 的 metadata 字段，为后续的精确过滤和多通道路由提供重要依据。
而 L2 构建的 BM25 则是独立的关键词倒排索引，主要用于处理报告中出现的具体编号、条款、金额等需要精确匹配的场景。两者作用层次不同，相互补充，共同构成系统的混合检索基础。



### 2. 为什么先聚类比直接向量搜索更准？（不是“只是词义”那么简单）

实际效果通常是：

- 在**中等语义距离**的总结句上（比如“履职监管不到位”“整改落实不彻底”这类），主题匹配准确率较高，能有效把检索范围从几万/几十万个片段缩小到几百个相关片段，大幅减少噪声。
- 在**高度抽象或语言转化极大**的总结句上，准确率会下降，但仍然比 flat（平面）向量检索强，因为它至少提供了一个“大概的方向”。


虽然底层依然依赖**向量语义相似度**，但**机制上有本质区别**，这让它在总结类场景中更有优势：

- **向量空间中的“局部密度” vs “全局搜索”** 直接在所有 chunks 上做向量搜索，是在**整个高维空间**里找最近邻。问题在于：embedding 空间里噪声很多，很多不相关的片段因为某些词重叠或向量“坍缩”（anisotropy）现象，也会得到较高的相似度分数，导致噪声多、排名混乱。
    
- **聚类先做了“语义分组”** BERTopic + HDBSCAN 在**离线阶段**就把所有片段根据向量相似性聚成了一个个**紧密的语义簇**（主题）。 每个主题簇内部的片段语义高度相关，簇与簇之间相对分离。 当报告中的总结句进来时，先匹配**主题向量（通常是簇的质心/centroid）**，相当于先找到“这是哪一类问题”，再只在这一类（或 Top N 类）里面做细召回。
    
    → 这就相当于从“在大海里捞针”变成了“在几个相关的池子里捞针”，**显著降低了错误答案的概率**。
    
- **额外增强机制让它更准**：
    
    - **c-TF-IDF 关键词**：每个主题不仅有一个向量，还有代表性的关键词，进一步提升主题表示的区分度。
    - **Qwen 生成的业务标签 + 手动维护**：把机器生成的“主题-12”变成“履职监管”“风险排查”等业务语言，大幅缩小了报告总结句与主题之间的语义鸿沟。
    - **双层检索 + 自动验证**：匹配到主题后，再落回具体 chunks，并做相似度校验，能过滤掉部分错配的片段。

总结一句话：**它不是简单的“词义匹配”**，而是**提前对语义空间做了结构化组织（clustering）**，让粗召回更有方向感，从而减少全局搜索带来的大量噪声，把全局搜索变成了有方向的局部搜索，从而有效排除了大量错误答案

不过
- 如果总结句的表述**过于抽象、主观，或与底稿原文的语义距离极远**（例如作者加入了很多隐性推理），主题匹配仍然可能不准或匹配到宽泛的主题。
- 聚类质量高度依赖 **BGE-M3** 的 embedding 能力和底稿数据的质量。如果底稿本身写作风格差异很大，聚类效果会受影响。
- HDBSCAN 会产生 **outliers（离群点）**，有些碎片化内容可能无法被很好地聚入任何主题。
