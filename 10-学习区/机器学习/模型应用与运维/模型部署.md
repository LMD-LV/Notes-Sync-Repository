

### 常见的使用方式

| 部署模式          | 核心逻辑                                            | 延迟 / 吞吐量     | 适用场景                   |
| ------------- | ----------------------------------------------- | ------------ | ---------------------- |
| 离线批量部署        | 模型对批量数据（如每日 / 小时级）离线推理，结果写入数据库 / 文件             | 高延迟、高吞吐量     | 报表生成、用户画像批量更新、推荐系统离线召回 |
| 在线实时部署        | 模型封装为 API（REST/gRPC），接收实时请求并返回结果                | 低延迟、低 - 中吞吐量 | 电商推荐、风控实时决策、语音识别       |
| 边缘部署          | 模型部署到终端设备（手机、工控机、IoT），本地推理不依赖云端                 | 极低延迟、低功耗     | 自动驾驶、智能家居、工业质检         |
| 流式部署          | 模型处理实时数据流（如 Kafka 消息），持续输出推理结果                  | 低延迟、高吞吐量     | 实时监控、日志分析、物联网数据处理      |
| Serverless 部署 | 模型部署到云厂商 Serverless 平台（如 AWS Lambda），按需付费、自动扩缩容 | 弹性伸缩         | 低访问量、突发流量场景（如小众功能接口）   |

- **离线导出模型（常见模式）**：训练 → 导出（`.pkl` / ONNX / SavedModel 等） → 上传/部署 → 提供预测 API（推理和训练分离）。这是最常见也最容易工业化的模式（可复现、性能可控、审计友好）。
    
- **按需训练/在线训练 / 内存中模型 + 动态重训（你描述的模式）**：服务启动后在内存中持有模型，提供训练接口（或上传训练集路径），当接收到新训练集时在服务内重新训练并切换到新模型（权重在内存）。也可以支持“同一模型权重下加载不同训练集再训练”的用法。可行，但要注意很多工程与安全边界。(注意同步,异步的控制方式) (这通常被称为 **"Fine-tuning as a Service"（微调即服务）** 或者 **"Continuous Learning / Incremental Learning"（持续学习/增量学习）**。)
	- 训练很耗时（数小时/天）且不能阻塞请求路径（应改用异步任务/批处理）
	- 多租户强隔离或高安全要求（需严格沙箱与权限控制）
	- **如果每次针对特定用户的数据训练一个专属模型**：这叫 **Multi-tenant ML（多租户机器学习）**。例如：你是一个SaaS平台，每个客户上传自己的数据，你给每个客户生成一个专用的分类模型。
	- **如果是在同一个大模型上不断修补**：这叫 **Incremental Learning（增量学习）**。
	- 需要严格可审计/可回滚的生产服务（静态导出模型更安全可控）。
	- 可能带来的风险是 训练带来的阻塞和超时,多并发的挑战,增量学习可能会导致准确率下降,脏数据的污染问题
	- 适用于 SaaS 平台、个性化推荐、或需要快速适应新概念的场景（如舆情监控）。

如果训练是增量式、持续学习，通常称为 **online learning / incremental learning**。如果每次都完全从头训练（full re-train），则叫 **retrain-on-request**。

### 常见的格式

| 格式                    | 核心特点                                       | 适用场景                                       | 优缺点                                |
| --------------------- | ------------------------------------------ | ------------------------------------------ | ---------------------------------- |
| pkl（Python pickle）    | Python 原生序列化，直接保存对象（如 sklearn 模型）          | Python 生态内快速原型、离线批量推理                      | 优点：简单；缺点：版本依赖、跨语言不可用、安全风险（反序列化漏洞）  |
| PMML（预测模型标记语言）        | XML 格式描述模型结构，独立于编程语言                       | 传统 ML 模型（树、线性回归）跨语言部署（如 Python 训练→Java 部署） | 优点：跨语言；缺点：不支持深度学习、复杂模型表达能力弱        |
| ONNX（开放神经网络交换格式）      | 微软 / 脸书主导，统一多框架模型格式（支持 sklearn/torch/tf 等） | 跨框架 / 跨语言部署、高性能推理                          | 优点：通用、工业级、支持深度学习；缺点：部分算子兼容需适配      |
| TensorFlow SavedModel | TF/PyTorch（转 TF）原生格式，包含计算图 + 权重            | TF/Keras 模型部署、云端推理                         | 优点：框架原生、性能优；缺点：仅限 TF 生态            |
| TorchScript           | PyTorch 专属序列化格式，将 Python 代码转为静态图           | PyTorch 模型高性能推理、边缘部署                       | 优点：脱离 Python GIL、速度快；缺点：仅限 PyTorch |
| MLflow Model          | MLflow 封装的「配置 + 权重」组合（指向 pkl/ONNX 等）       | 适配 MLflow 生态的全流程部署（注册→部署）                  | 优点：自带环境管理、多格式兼容；缺点：依赖 MLflow 生态    |
| TFLite                | TF 轻量化格式，针对移动端 / 边缘设备优化（量化、剪枝）             | 手机 / 嵌入式设备（边缘部署）                           | 优点：体积小、低功耗；缺点：仅限移动端                |
| OpenVINO IR           | 英特尔主导，针对 x86 / 边缘硬件优化的模型格式                 | 英特尔硬件上的高性能推理（如工控机）                         | 优点：CPU 推理速度提升 5-10 倍；缺点：硬件绑定       |
|                       |                                            |                                            |                                    |

**PMML（Predictive Model Markup Language，预测模型标记语言）** 是一种基于 XML 的标准化语言，用于**跨平台、跨工具地描述和共享机器学习模型**。PMML 的作用就是**将模型的 “输入数据格式、预处理逻辑、模型参数、输出规则” 全部用标准化 XML 描述**，形成一个可移植的 “模型文件”。任何支持 PMML 的工具（无论开发语言），都能通过解析这个文件直接加载模型并进行预测，实现 “一次训练，多端部署”。但对于深度学习模型或超高性能需求场景，需搭配 ONNX 等其他标准使用


### MLflow工具

**MLflow 是一个覆盖机器学习生命周期的工具集**，包含四个主要模块：Tracking、Projects、Models、Model Registry。它既能做实验跟踪，也能做模型注册、打包与部署。
核心是MLops的产物

MLmodels配置文件 : 描述“模型的上下文与调用方式”（类似说明书 + 配置清单）。它记录了模型支持的 _flavors_（推理接口类型）、依赖环境（conda/requirements）、输入输出 signature、示例输入、以及 artifact 路径等。部署时 MLflow 用这个元数据去正确加载模型并提供统一的推理 API（pyfunc 等）。
