#### Agent组成

LLM+外部工具+循环(不断地思考、行动、观察结果、再思考，直到任务完成)

思考模块+规划模块+记忆模块+工具模块

目前商业的成熟方案是运行在 Firecracker,做到隔离和弹性扩容

**“Profile 隔离 + Delegation 委派 + Honcho 用户建模”**，放在一起是在描述一套**多 Agent 协同工作的架构设计思路**。

可以简单理解为：**如何让一群 AI 既各司其职、又能高效合作，同时还能共同记住并理解一个用户。**

**Profile 隔离”就是给每个 Agent 一个独立的身份档案和记忆空间。**

- **里面包含什么**：它的角色设定、专业知识库、可调用的工具、以及它自己与用户交互的那部分短期记忆。
- **为什么要隔离**：
    
    - **安全与专注**：代码执行器看不到你给“心理咨询师” Agent 的私密对话，也避免它被无关信息干扰。
    - **避免冲突**：不同角色有自己的行为准则，隔离后不会出现“既要幽默又要严肃”的人格分裂。

### 2. Delegation 委派（任务分派与协同）

有了多个专家 Agent 后，需要一个机制来决定“谁来干活”。

**“Delegation 委派”就是一个 Agent（通常是主控或协调者）把复杂的任务拆解，并派发给最擅长的子 Agent 去执行。**

- **流程**：
    
    1. 主 Agent 接到用户指令：“帮我研究一下某公司，并生成一份 PPT。”
        
    2. 它把“研究公司”委派给**研究员 Agent**。
        
    3. 把“写代码抓数据”委派给**代码 Agent**。
        
    4. 把“生成 PPT”委派给**文档 Agent**。
        
    5. 最后汇总结果。
        
- **核心价值**：这是一种横向协同，让专门的人（Agent）做专门的事，主 Agent 不陷入执行细节，只做管理和整合。


### 3. Honcho 用户建模（统一的用户记忆）

这是三个词里最关键且最特别的一个。**Honcho 实际上是一个开源的用户记忆框架**（由 Plastic Labs 开发），专门用来给 AI 应用做“用户档案”的。

在多 Agent 场景下，最头疼的问题是：每个 Agent 对用户的了解都是碎片化的。研究员 Agent 知道你喜欢详细数据，但文档 Agent 可能不知道你喜欢图表风格的 PPT。

**“Honcho 用户建模”就是引入一个独立的、统一的“用户记忆层”。**

- **它做什么**：
    
    - **长期记忆**：它会自动从你和各个 Agent 的交互中，提取并沉淀你的偏好、习惯、知识背景等信息。例如，你反复让研究员查环保数据，Honcho 会记住“该用户关注 ESG 议题”。
        
    - **全局共享**：当任何一个 Agent 被委派任务时，它都可以先去 Honcho 那里读取关于你的最新档案。这样，代码 Agent 在生成图表时，就能主动把色调调成你喜欢的样式。
        
- **与 Profile 隔离的区别**：Profile 隔离是 Agent 的“工作技能”私有化，而 Honcho 用户建模是“对用户的认知”全局化、共享化。


它们构成了一套**既分工明确、又体验一致**的多 Agent 系统：

1. **用户** 提出请求。
2. **主协调 Agent** 先去 **Honcho 用户模型** 里查一下：这个人是谁？有什么习惯？
3. 带着对用户的了解，主 Agent 进行 **Delegation 委派**，把任务拆解给各个子 Agent。
4. 每个子 Agent 在 **Profile 隔离** 的保护下，用自己独有技能干活，互不干扰。
5. 子 Agent 在执行过程中，可能又需要读取或更新 Honcho 里的用户记忆，让下次协作更默契。



### 外部工具

#### Function Call
底层的调用工具函数,解决了 什么时候调用+传什么参数的问题
实现的具体步骤
1,定义函数 : 开发者预先告诉 LLM「你手边有哪些工具可以用」，用 JSON 格式描述每个函数的名字、功能说明和参数
2,模型判断 : 用户提问后，LLM 分析用户的意图，自己判断「要回答这个问题，我需要调用哪个函数」
3,执行函数: **LLM 自己并不执行函数**。它只是输出了「我想调用这个函数，参数是这些」的结构化指令
4,生成回答 

Function Call 是一次性的「单步调用」，LLM 判断需要调用一个函数，调用完就结束了。而 Agent 是「循环调用」，Agent 在一个循环中反复使用 Function Call，每次调用后观察结果，再决定下一步要不要继续调用其他函数。


#### MCP协议
（Model Context Protocol，模型上下文协议）,统一了连接外部工具的标准
组成架构为:
- 首先是 **MCP Host（宿主）** ，就是你使用的 AI 应用，比如 Claude Desktop、Cursor 编辑器、你自己开发的 Agent 应用。它是整个交互的发起方。
- 然后是 **MCP Client（客户端）** ，它住在 Host 里面，负责跟 MCP Server 通信。你可以把它理解为"翻译官"，Host 想要什么能力，Client 就去跟对应的 Server 沟通。
- 最后是 **MCP Server（服务端）** ，它负责对外暴露具体的工具能力和数据资源。比如有一个 GitHub MCP Server，它能提供"搜索代码""创建 Issue""查看 PR"等工具。一个 Slack MCP Server 能提供"发送消息""搜索频道"等工具。



### Agent常见的工作模式

ReAct模式(Reasoning + Acting,  推理+行动):  实际执行的时候三步循环, 思考+行动+观察

Plan-and-Execute模式(先想好再做): 第一阶段是规划，Agent 先把完整的执行计划想清楚；第二阶段是执行，按计划逐步完成，不用每步都重新思考全局。比较节省token,但是容错率低, 不够灵活，如果执行到第 3 步发现情况变了，原来的计划可能就不适用了。所以也有这么个做法是在执行过程中加入「重新规划检查点」，每隔几步检查一下计划是否还靠谱。

Reflection(做完再检查): 核心思想是 Agent 完成任务后不急着交付，而是先自我检查一遍,
具体执行的时候, 可以使用 单个Agent自己检查, 或者另一个Agent来检查(特别适合对质量要求高的场景，比如代码生成、法律文书、学术论文等)

Multi-Agent(团队协作): 让多个专业化的 Agent 各司其职，比如一个负责规划、一个负责搜集信息、一个负责写代码、一个负责测试，通过协作来完成复杂任务。

Self-Ask 自问自答

Thinking and self-Refection 思考并自我反思

### 多Agent协作

一个多 Agent 系统中，每个 Agent 内部可能用的是 ReAct 模式，整体协作用的是 Multi-Agent 模式，最后还有一个 Reflection 环节来检查质量。

A2A（Agent-to-Agent）

让不同的 AI Agent 能够**互相发现、互相通信、互相委派任务**

第一个是 **Agent Card（智能体名片）** 。每个支持 A2A 的 Agent 都会发布一个 JSON 格式的"名片"，描述自己的身份、能力、擅长的领域、支持的交互方式、认证要求等信息。其他 Agent 通过读取这个名片来了解"这个 Agent 会什么，我能请它帮什么忙"。这就像你在 LinkedIn 上看到一个人的简历，知道他的技能和经验后，才决定要不要跟他合作。

第二个是**任务（Task）** 。A2A 中的所有协作都围绕"任务"展开。一个 Client Agent（发起方）创建一个任务，发送给一个 Remote Agent（执行方）。任务有完整的生命周期，从创建、处理中、到完成或失败，每个状态变化都有明确的定义。这让双方能清楚地跟踪任务进展。

第三个是**消息和制品（Message & Artifact）** 。Agent 之间通过消息来沟通过程中的信息，通过制品来传递最终结果。比如一个研究 Agent 完成分析后，会把分析报告作为制品返回给请求方。

首先它完全基于现有的 Web 标准，HTTP 用于传输、JSON 用于消息格式、SSE 用于实时流式通信。这意味着不需要引入任何新的基础设施，现有的 Web 技术栈就能直接支持。

其次它支持**异步和长时间运行的任务**。Agent 之间的协作往往不是一瞬间能完成的，一个研究 Agent 可能需要几个小时才能完成深度调研。A2A 对此有完整的支持，包括任务状态查询、进度更新、断线重连等。

另外它是**模态无关的**，Agent 之间不仅能传递文本，还能交换音频、视频、图像、结构化数据等各种格式的内容。


多 agent 协作已经分化成四条路径：CrewAI 25k 做角色编排、AutoGen 35k 做对话协作、MetaGPT 50k 模拟软件公司、Mem0 52k 做记忆基础设施。
核心都是多Agent编排框架


从单LLM内核到复合认知架构”的核心思路：我们不再强求一个LLM去扮演所有角色，而是用不同的技术组件分别实现系统1和系统2，让它们协作。

架构蓝图大致如下：

- **系统1（直觉生成器）**：由**一个轻量快速的LLM** 担任。它负责快速产生多个可能的想法、答案或下一步行动。它不保证正确，只负责“联想”和“提出假设”。
- **系统2（逻辑审查官/规划器）**：这是架构演进的关键，它可以由多种技术手段组合而成，而不是一个单一的模型：
    - **慢思考LLM**：可以调用更强大的模型，用复杂的提示词对系统1的结果进行批评、修正，形成自我反思循环。
    - **符号推理引擎**：将问题翻译成数学逻辑表达式，用规则进行绝对可靠的推导。
    - **树搜索/规划器**：如蒙特卡洛树搜索，在多个推理分支中模拟推演，用“世界模型”预测结果，选择最优路径。
    - **形式验证工具**：对生成的代码或方案进行数学上的正确性验证。
    - **外部记忆验证**：把Mem0这类记忆层融入系统2，让它在做决策时能检索、核对历史经验和事实。



多Agent落地的问题

- **身份与权限层**：Agent 以谁的身份行动？跨系统如何认证、授权？没有这层，多 Agent 只能是 Demo。
- **目标与约束层**：人类如何可靠地为 Agent 设定长期目标、边界和价值观？如何防止目标被篡改或误解？
- **评估与可观测层**：多 Agent 协作时，如何追踪决策链路、测量性能、诊断失败？目前几乎空白。
- **现实连接层**：真正获取现实世界信息（不是单次搜索），触发真实世界效应（API 之外），以及持续的反馈循环。

1. **从“语言驱动的流程”到“世界模型驱动的推理”**  
    现在的 Agent 靠 prompt 推理下一步，太依赖语言表面。真正的演进可能是让 Agent 构建**内部世界模型**，能模拟行动后果，而不是每次靠 LLM 实时想。
2. **从“固定角色协作”到“自组织能力市场”**  
    也许未来的多 Agent 系统不像公司，更像**协议经济**。Agent 动态发现彼此的能力，协商价格，临时组队，任务结束解散。这需要全新的发现、协商和信任协议，远超现在的“编排”。
3. **从“单 LLM 内核”到“复合认知架构”**  
    真正可靠的 Agent 很可能会把 LLM 作为组件之一，结合符号推理、搜索、记忆、专用模型等。比如 Kahneman 的快慢思考双系统设计。这种**认知架构**的演进，比编排框架更底层。
4. **从“封闭多 Agent”到“人、Agent、环境共生”**  
    多数框架把人排除在外或只给一个接口。现实是需要人与 Agent 在共享环境中持续交互、监督、干预。这需要全新的交互范式和责任模型。
