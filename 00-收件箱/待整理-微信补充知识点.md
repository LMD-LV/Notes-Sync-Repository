## 1. 大模型作用在数据分析的几个痛点

- 业务概念的分歧
- 知识库的信息滞后
- 检索的质量
- 隐形规则

解决思路：**业务语言 → 标准口径 → 权威字段 → 合法规则**

治理底座 + 语义层标准化 + 模块化技能体系 + 全链路校验闭环（关键词：数据治理）

## 2. Agent 工程实践要点

长期运行 Agent 的能力关键词：looping coding（循环编码）、定时任务、工作空间隔离、共享知识体系、连接器 MCP、子 Agent。

给 Agent 定义任务的四条原则：

1. 完成标准要可以被机器验证。
2. 边界条件要跟完成标准一起定义。
3. 要有失败的降级方案。
4. 目标要分层。

## 3. 四代 Engineering：能力分层

| 层 | 核心思想 | 核心能力 |
| --- | --- | --- |
| Prompt Engineering | 好好说话，AI 会更懂你 | 语言表达 |
| Context Engineering | 光说话不够，得给 AI 足够的信息 | 信息筛选和组织 |
| Harness Engineering | 光给信息也不够，得给 AI 设规则和约束 | 系统设计和规则制定 |
| Loop Engineering | 光设规则也不够，得让整个系统能自己跑起来 | 目标定义和管理 |

## 4. Agent 查数据：四层信息来源

Agent 查数据，四层信息来源：

1. **语义层** —— 业务语言的标准化映射
2. **血缘层** —— 字段/表的来龙去脉
3. **查询库** —— 把历史查询提炼成结构化的参考文档和可复用的查询模式
4. **业务上下文** —— 文档的质量会直接影响效果

相关概念：成对 Skills（Pair Skills）。

## 5. RAG 流程的效果评估

把评估拆成两层：

**第一层：检索层评估** —— 不管 LLM 的输出，只看「该召回的文档有没有被召回到」。
指标：**Hit@K**，正确答案有没有出现在检索结果的前 K 条里。如 Hit@5 = 0.8 表示 80% 的问题，其对应答案出现在前 5 条检索结果里。可自动化批量跑，快速定位检索是否是系统瓶颈。

**第二层：端到端评估** —— 用 RAGAs 这类框架自动打分，三个维度：

- **Faithfulness（忠实度）**：LLM 的答案有没有编造知识库里没有的内容
- **Answer Relevancy（答案相关性）**：答案和问题是否对应，防止「答非所问」
- **Context Recall（上下文召回率）**：检索出来的内容是否覆盖回答问题所需的全部知识

## 6. 知识编译（Knowledge Compilation）理念

核心理念：让知识库从一个被动的「仓库」变成一个主动的「系统」，解决知识管理中「收藏即遗忘」的痛点。

核心设计（raw/wiki 分层）：

- `raw/` 文件夹：存放原始资料（文章、笔记等），是「原料」
- `wiki/` 文件夹：存放经过 AI 整理的知识页面（概念、主题等），是「成品和半成品」
- `AGENTS.md` 规则文件：给 AI 的「工作说明书」，定义它如何处理和整理知识

流程：AI 承担知识整理的「体力活」——放入新文章后，AI 负责提炼观点、创建概念页、建立双向链接，逐步构建互联的知识网络。提问时，AI 优先基于已整理好的 `wiki/` 层回答，而不是每次都在原始资料里「大海捞针」。

## 7. 统一存储底座：结构化 + 非结构化 + 多媒体 + 向量共存

让结构化表（订单/用户）、非结构化文档（PDF/网页）、多媒体（图片/视频）、向量 Embedding 共存于同一存储底座。方案选择：

### 方案一：统一湖仓平台（Lakehouse Platform）

- 利用 Paimon 或 Iceberg 等开放表格式，在一套存储系统内同时管理结构化表、非结构化文件和向量数据
- 元数据层由统一的 Catalog 管理（如阿里云 DLF、腾讯云 TCLake），实现「一次入湖、多处可用」
- 局限：原生湖仓在极低延迟、高并发的向量检索场景下，性能可能不如专用向量数据库。业界出现 Paimon + Milvus 协同方案：Paimon 负责存储治理，Milvus 负责高性能检索

### 方案二：多模数据库

- 一个数据库内核原生集成向量、全文、宽表、时序、KV 等多种数据模型；数据写入一次，即可通过统一 SQL 接口跨模型查询
- 例：阿里云 Lindorm，原生支持向量、全文、宽表、时序、KV 五模一体。相比 Milvus + ES + Redis 拼接方案，组件从 3 个减为 1 个，P99 延迟降低 80%，TCO 降低 55%
- 局限：多为云厂商商业产品，开源选项较少；单一模型的极致性能（如极大规模向量检索）可能不如专用单模数据库

### 方案三：AI 原生存储格式（AI-Native Storage Format）

- 采用专为 AI 设计的存储格式，如 **Lance**：支持向量、媒体、元数据的统一存储与零拷贝随机访问
- 克服传统列式格式（如 Parquet）在随机读取和向量检索上的 I/O 瓶颈

## 8. Skill 体系

- 不要把所有技能一锅炖。**通用技能和任务技能有本质差异，分而治之**效果远好于一刀切。
- Skill 0.5 的「0.5」哲学：随着技能库持续扩张，模型只需要内化稳定的通用底座，任务技能可以无限外挂——这是一个可持续扩展的架构。
- 难度分层训练和反捷径探测是两个独立贡献：前者解决**冷启动**问题，后者解决**过拟合**问题。这两个思路不限于技能训练，也适用于其他 RL 场景。
- Flink Skill 是连接 Agent 大脑与执行动作的神经中枢：通过 **SOP 注入**将专家运维经验固化为 Agent 原生能力，通过**逻辑封装**屏蔽工具调用复杂度。一句话总结：**Memory 是 Agent 的资产，工具是设备，Skill 是生产工艺。**

## 9. 世界模型两种形态：LWM vs 狭义世界模型

### Large World Model（LWM）大世界模型

定位：超长上下文多模态自回归模型。不止看懂静态画面，学习世界时序动态、事件先后因果，朝理解现实世界演变规律方向设计。

特点：

- 文本、图片、长视频统一编码成 token，扔进同一个 Transformer
- 支持最高 1M tokens 超长序列，可一次性处理几十分钟～1 小时完整视频
- 任务：长视频问答、长文档检索、图文对话、短视频生成
- 关键局限：**不是狭义动力学世界模型**——只是看懂一段已经发生的长视频，不能接收动作指令、模拟「做出某个动作之后世界会如何演变」

适合研究/二次开发：长视频内容分析、影视自动摘要、监控长录像检索；超长文档知识库、法律/书籍全文问答；多模态智能 Agent（需要理解时序画面）。

### 狭义标准世界模型（LeCun JEPA、Sora、Genie、机器人世界模型）

- 输入：当前观测 + 动作 a_t；输出：执行动作之后未来的世界状态
- 核心能力：**反事实模拟**，在「脑子里」推演行动带来的结果——「如果我做 A，世界会发生什么」，面向动态物理、具身智能
- 典型例子：
    - Sora：给定画面 + 指令，推演后续视频画面
    - 机器人世界模型：「机械臂伸手」→ 预测会不会碰倒杯子
- 这是能模拟世界动态因果、可交互仿真的路线

## 10. Honcho：开源用户记忆框架

Honcho 由 Plastic Labs 开发，用于为 AI 代理提供长期用户记忆和个性化。在多 Agent 协同中，可用于**统一用户建模**：让所有 Agent 访问同一个用户画像，从而提供一致体验。
