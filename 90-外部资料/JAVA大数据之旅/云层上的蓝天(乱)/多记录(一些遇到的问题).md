## 1.hive 自定义udf函数

类比

```java
import org.apache.hadoop.hive.ql.exec.Description;
import org.apache.hadoop.hive.ql.exec.UDF;
import org.apache.hadoop.io.Text;

import com.alibaba.fastjson.JSONArray;
import com.alibaba.fastjson.JSONObject;

@Description(name = "get_json_object",
             value = "_FUNC_(jsonString, jsonPath) - Extracts a JSON object or element specified by jsonPath.",
             extended = "Example:\n" +
             "  > SELECT get_json_object('{\"name\":\"John\", \"age\":30}', '$.name') as name;")
public class GetJsonObjectUDF extends UDF {

    /**
     * 从JSON字符串中提取指定的JSON对象或元素
     * @param jsonString 包含JSON数据的字符串
     * @param jsonPath 提取的JSON对象或元素的路径
     * @return JSON对象或元素的字符串表达式，如果未找到则返回null
     */
    public Text evaluate(Text jsonString, Text jsonPath) {
        if (jsonString == null || jsonString.toString().isEmpty() ||
            jsonPath == null || jsonPath.toString().isEmpty()) {
            return null;
        }
           try {
            JSONObject jsonObject = JSONObject.parseObject(jsonString.toString());
            Object result = jsonObject != null ? jsonObject.eval(jsonPath.toString()) : null;

            if (result != null) {
                return new Text(result.toString());
            }
        } catch (Exception e) {
            // 处理异常，根据需要进行操作
            e.printStackTrace();
        }

        return null;
    }
}
```

## 3.flink作业问题：

**问题一**

flinkcdc全量同步完表格后，对数据计算，数据进入计算逻辑时没有按预想watermark的升序进行计算，是乱序的。flinkcdc2.2.1，我全量从头同步一张表a（product\_Id，number，create\_time，update\_time），按照表里的update\_time作为watermark（ts），数据在flinkui界面是能看到完全同步过来了，然后按照product\_id维度，对数据开小时滚动窗口聚合sum（number）。然后问题出现了，我输出的时候应该是一个小时一个产品一条数据，最后输出就几条数据（应该输出几千条），我想着应该是watermark乱了然后更新很快就结束了。我尝试在计算逻辑部分先给a表的watermark字段排个序或者update\_time排个序，但是还是不行

MySQL CDC源表如何工作，会对数据库造成什么影响？

在启动模式为initial（默认值）时，MySQL CDC源表会先通过JDBC连接MySQL，使用SELECT语句读取全量的数据，并记录Binlog的位点。全量阶段结束后，再从记录的位点开始读取Binlog中的增量数据。

全量阶段时，由于通过SELECT语句查询数据，MySQL服务的查询压力可能会增加。增量阶段时，需要通过Binlog Client连接MySQL读取Binlog，当使用的数据表增加时，可能出现连接数过多的问题。可以通过如下MySQL查询来查看最大连接数：

```java
show variables like '%max_connections%';
```

经由测试发现，mysqlcdc的确是全量读取表的时候是以jdbc的形式读取，数据会并行，乱序程度很大，此时想要小范围聚合计算数据数据大概率计算不准，解决方法：

设置很大的允许迟到（占内存）

设置很大的窗口（占内存）

先计算历史再计算实时，让二者结合（推荐使用）。如开天窗口：先在T日启动实时计算数据将数据写入含主键的表中，再将历史数据在T+1日全量分组聚合为想要的数据插入更新到含主键的表中，这样T日数据被历史分组计算覆盖为正确的数据，同时历史计算完毕后，实时数据会覆盖T+1日数据为当前实时计算结果。

## 5.当与多系统交互问题

1）上游给数不及时，时间无法保证，怎么调度取数？

离线：dataworks可以配置轮询节点，到点轮询上游批量执行情况（需要上游批量跑完后往对应表格插入执行记录及状态），成功则开始跑下游数据，确保数据正常。

实时：上游没数就不消费，按事件时间不会有问题，有数据了会继续消费。

2）给下游数据，如何通知我数据正常，你可以消费了。

每个批量（或者整个系统批量跑完后），向跑批记录里添加一条记录来告诉下游，下游来轮询。

3）测试环境如何多系统联合自动跑批（类似于生产到点了大家都会启动批量，开闸放水，水会无阻拦自动跑向下游。测试环境每个系统都有个闸门，需要大家输入日期手动跑批，就很麻烦，所以设置上游就一个闸门，下游跟随上游运行，完全模拟生产环境）。一般按日批调度，所以需要一个切日的逻辑，各系统造好一日批量数据后，上游通知下游要开始跑批了，就开始切日，切日后跑数，跑完后造第二天数，以此类推。模拟生产环境。

实现：需要借助轮询上游执行记录，并且需要调取所使用工具的api，如dataworks，将整个项目根节点api暴露出来，使用flinkcdc去读取上游数据，读取到切日了，就调用api运行自己系统流程。

```sql
-- pgsql-cdc同步pg库，需要开启库的create权限，
-- 表的select权限，复制流权限，full复制标识符，发布表
GRANT create ON DATABASE hive to hive;
-- 表的select权限
GRANT select on table hive to hive;
-- 复制流的权限
ALTER ROLE hive replication;
-- full复制标识符，full则能进行update和delete。否则只能insert
ALTER TABLE hive REPLICA IDENTITY FULL;
-- 查询是否开启full复制标识符
select relreplident from pg_class where relname='hive';

-- 查询当前用户对所有表的权限
SELECT * FROM information_schema.table_privileges WHERE grantee = 'hive';

-- 查询当前用户对所有库的操作权限
select a.datname,b.rolname,string_agg(a.pri_t,',') 
from (select datname,(aclexplode(COALESCE(datacl, acldefault('d'::"char",datdba)))).grantee as grantee,(aclexplode(COALESCE(datacl, acldefault('d'::"char", datdba)))).privilege_type as pri_t from pg_database where datname not like 'template%') a,pg_roles b 
where (a.grantee=b.oid or a.grantee=0) and b.rolname='hive' 
group by a.datname,b.rolname;

-- 设置表为可以发布状态，所有表，可以用 pubname is not null
update pg_publication set puballtables=true where pubname ='hive';

-- 发布相应的表 也可用 all tables
CREATE PUBLICATION dbz_publication FOR table hive;
-- 查询哪些表可以发布
select * from pg_publication;
delete from pg_publication where oid is not null;
-- 查询已经发布的表
select * from pg_publication_tables;
delete from pg_publication_tables
```

## 18.记一次jdbc问题

具体报错信息

com.mysql.jdbc.exceptions.jdbc4.CommunicationsException: The last packet successfully received from the server was 385,290,819 milliseconds ago. The last packet sent successfully to the server was 385,290,820 milliseconds ago. is longer than the server configured value of ‘wait\_timeout’. You should consider either expiring and/or testing connection validity before use in your application, increasing the server configured values for client timeouts, or using the Connector/J connection property ‘autoReconnect=true’ to avoid this problem.

  

错误原因：

MySQL数据库一般默认的连接等待时间为28800s(即8小时)，超过8h，数据库会断开这个连接，但是应用不知道这个连接已经被数据库断开，所以链接池认为该连接是有效的，在下次请求时，连接池会把自己认为有效，但是数据库认为无效的连接分配出去，便会导致如上错误；

查询了mysql数据库的wait\_timeout

SHOW GLOBAL VARIABLES LIKE ‘%wait\_timeout%’;

发现确实是8小时

  

加上idleConnectionTestPeriod:用来配置测试空闲连接的间隔时间,如果发现超时，会自动去掉。默认0，不进行测试，单位s(秒)

更新后的配置文件，idleConnectionTestPeriod只要设置比数据库28800秒（8小时）小就可以，我这边设置的是3600秒即一小时进行检测。
