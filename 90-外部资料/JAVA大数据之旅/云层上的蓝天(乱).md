# Doris

## Doris Join 调优方法

Doris Join 调优的方法：

-   利用 Doris 本身提供的 Profile，去定位查询的瓶颈。Profile 会记录 Doris 整个查询当中各种信息，这是进行性能调优的一手资料。
-   了解 Doris 的 Join 机制，这也是第二部分跟大家分享的内容。知其然知其所以然、了解它的机制，才能分析它为什么比较慢。
-   利用 Session 变量去改变 Join 的一些行为，从而实现 Join 的调优。
-   查看 Query Plan 去分析这个调优是否生效。

上面的 4 步基本上完成了一个标准的 Join 调优流程，接着就是实际去查询验证它，看看效果到底怎么样。

如果前面 4 种方式串联起来之后，还是不奏效。这时候可能就需要去做 Join 语句的改写，或者是数据分布的调整、需要重新去 Recheck 整个数据分布是否合理，包括查询 Join 语句，可能需要做一些手动的调整。当然这种方式是心智成本是比较高的，也就是说要在尝试前面方式不奏效的情况下，才需要去做进一步的分析。

​  

使用场景：hive catalog查询维表，doris内表为主表

1.内外表多表关联，将最大表优先与最小表join（裁剪）；无小表情况下，直接使用shuffle join性能能提升很多（因为涉及外表，doris没法自动切换brodercast join 和shuffle join） 。问题：如何确定大小表？

注意：

Bucket Shuffle Join只生效于Join条件为等值的场景，且类型一至

-   Bucket Shuffle Join只作用于Doris原生的OLAP表，对于ODBC，MySQL，ES等外表，当其作为左表时是无法规划生效的。

2.分区表，优先使用分区字段过滤

3.分区按created\_date、分桶可以使用业务主键（业务主键多用与join），目前ods层使用的是物理主键作为分桶key。问题：现在改动工作量会很大，影响面广，建议之后的表接入按此逻辑？

4.Broadcast Join与Shuffle Join， Bucket Shuffle Join 性能对比（网络开销、内存开销）：3B、A+B、B

# Runtime Filter

Runtime Filter主要用于大表join小表的优化，如果左表的数据量太小，或者右表的数据量太大，则Runtime Filter可能不会取得预期效果。

## Runtime Filter的规划规则

1.  只支持对join on clause中的等值条件生成Runtime Filter，不包括Null-safe条件，因为其可能会过滤掉join左表的null值。
2.  不支持将Runtime Filter下推到left outer、full outer、anti join的左表；
3.  不支持src expr或target expr是常量；
4.  不支持src expr和target expr相等；
5.  不支持src expr的类型等于HLL或者BITMAP；
6.  目前仅支持将Runtime Filter下推给OlapScanNode；
7.  不支持target expr包含NULL-checking表达式，比如COALESCE/IFNULL/CASE，因为当outer join上层其他join的join on clause包含NULL-checking表达式并生成Runtime Filter时，将这个Runtime Filter下推到outer join的左表时可能导致结果不正确；
8.  不支持target expr中的列（slot）无法在原始表中找到某个等价列；
9.  不支持列传导，这包含两种情况：

-   一是例如join on clause包含A.k = B.k and B.k = C.k时，目前C.k只可以下推给B.k，而不可以下推给A.k；
-   二是例如join on clause包含A.a + B.b = C.c，如果A.a可以列传导到B.a，即A.a和B.a是等价的列，那么可以用B.a替换A.a，然后可以尝试将Runtime Filter下推给B（如果A.a和B.a不是等价列，则不能下推给B，因为target expr必须与唯一一个join左表绑定）；

10.  Target expr和src expr的类型必须相等，因为Bloom Filter基于hash，若类型不等则会尝试将target expr的类型转换为src expr的类型；
11.  不支持PlanNode.Conjuncts生成的Runtime Filter下推，与HashJoinNode的eqJoinConjuncts和otherJoinConjuncts不同，PlanNode.Conjuncts生成的Runtime Filter在测试中发现可能会导致错误的结果，例如IN子查询转换为join时，自动生成的join on clause将保存在PlanNode.Conjuncts中，此时应用Runtime Filter可能会导致结果缺少一些行。

❓Q1 mysql与doris的varchar长度映射关系如何？  
💡A1 如下：

```plain
MySQL Varchar * 3 = Doris Varchar

原因：
1. MySQL 中 varchar(n) 中括号中 n 代表字符的个数，并不代表字节个数
2. Doris 中 VARCHAR(M) 中括号M代表字符的长度
3. 英文字符占1个字节，中文字符占3个字节，因此直接将现有 Doris 表中 varchar 类型字段长度调整为原来的 3 倍（即能兼容全是中文字符的情况）
```

❓Q2 insert into select慢怎么排查？  
💡A2 insert into select 慢，可以根据这个流程排查下：

```plain
1. 通过设置session var dry_run_query = true 来对问题进行细分：
 a. 如果设置 dry_run_query = true 之后变快很多，那么就是数据分发以及存储节点慢了；
 b. 如果设置 dry_run_query = true 之后依然很慢或者跑不出来，那么就是查询慢了。

-- dry_run_query = true 时，只跑查询部分，不在跑数据分发以及存储，所以可以用来快速排查是不是查询慢了。
-- 2.0.2-rc05 之后支持的
注意：dry_run_query 不要设置为 global，并且打开后需要设置回去，不然会查不到数据。

2. 如果是数据分发或者存储节点慢
可以通过 top -H 以及 IOutil 的信息来判断是 cpu 还是 IO 瓶颈
```

❓Q2 查询报错：[E-230]missed\_versions is empty

💡A2 如下：  
解决方案：调大be.conf的tablet\_rowset\_stale\_sweep\_time\_sec参数，并重启BE节点  
参数说明：这个参数主要是加大了合并版本的清理时间，尽可能避免刚好查询时需要的版本被合并清理了（写入过于频繁场景容易出现），举个例子：有张表table\_a里未合并清理的版本号是1-9，那么这个时候去执行 select \* from table\_a 它会去查询最新的version 9的数据，如果这段时间table\_a同时有写入，版本变成了1-10并且触发compaction及满足tablet\_rowset\_stale\_sweep\_time\_sec要去清理合并过的版本，变成了一个最新的查询版本1-10，那么这个时候version 9（1-9）就无法查询了，则会出现 select \* from table\_a 需要的version 9不存在miss从而报missed\_versions is empty  
BE参数说明可以查阅BE配置项：  
[https://doris.apache.org/zh-CN/docs/admin-manual/config/be-config](https://doris.apache.org/zh-CN/docs/admin-manual/config/be-config)

# 二、数据开放共享

## 1.概念发展

政府信息公开->开放政府数据->政府数据开放共享

## 2.推进数据开放共享

国家在行动

## 3.数据开放共享的方式

### 3.1 数据开放

主要是值政府数据面向公众开放。主要是一些非敏感、不涉及个人隐私的数据，且这些数据经过加工或者二次聚合任不会产生敏感数据的数据。

### 3.2 数据交换

主要是政府部门之间、政府与企业之间通过签署协议或者合作的方式开展的非盈利性数据开放共享

针对非敏感数据，在信用较好或者有关联的实体之间提供数据交换机制；针对敏感数据封装在业务场景中的闭环交换。

### 3.3 数据交易

对数据明码标价进行买卖。

主流：大数据交易所（交易中心）

其他：数据资源企业、自身拥有大规模数据的企业等

## 4.数据开放共享难题

### 4.1 无意愿开放共享

数据的价值在于利用、流动，在于整合分析挖掘，且数据的价值具有时效性，时间久了就慢慢贬值了。

1）没能正确认识到数据的价值，将数据束之高阁，不加任何开发和利用，更不知道共享。

2）太过于了解数据的价值，如同BAT各自互为竞争对手，都不愿意把自己的数据共享出来。

### 4.2 无胆量开放共享

1）数据的开放设计很多既有挑战性又很复杂的问题，均会家中数据主题在开放数据共享是的顾虑。有时开放数据会惹来麻烦。

2）数据质量问题，造假数据等，不敢公开共享。

### 4.3 无本领开放共享

1）数据的分析和处理难度大

2）信息系统中的数据是异构的，钥匙箱信息系统间的互联互通，必须 转换数据结构的方式来实现。

3）开放共享的法律法规十分匮乏

# 三、数据产权

### 1.三个核心问题：

数据归谁所有、谁可以是使用数据、数据收益如何分配

##### 2）离线计算

hive+MapReduce：从优点看，hive基于mr支持分布式批处理计算，同时支持以sql操作的方式对hdfs数据进行计算和统计分析，操作简单，容错性和扩展性好。缺点就是高延迟、查询和计算都很慢，使用于海量数据的批处理操作和分析场景。

spark：微批次处理设计机制，用统一的框架和引擎支持批处理、流处理计算、查询、机器学习等功能。SQL语句丰富、api功能完备简单易用，微批次流处理适合秒级延迟。

### 4.数据建模：让数据资产化

#### （1）建模前的问题

**困境一：**

无统一的组织和规划，对业务数据缺乏顶层的设计和抽象，大部分只会根据采集的业务数据进行烟囱式开发。数据工作者忙于各种取数和临时数据需求，没有经理规划全局的模型。个别来看能快速实现需求，但是从整体看，效率低下，重复工作多，指标的准确性没有保障，存储和计算资源浪费严重。

**困境二:**

取数有很多不同的路径，不同的人会创建不同的表、关联不同的表，指标准确性没有保障，取数时效性也缺乏保障。同一指标对于不同人往往有不同理解。

**困境三：**

空有数据量、而非“价值数据”。

**困境四：**

各系统数据源涉及数据的更新，或者表格字段等元数据的更改，由于下游抽数者多，上游系统又没有及时通知变更，则会导致数据的不一致，甚至数据出错（如抽取文件，字段数不一样则会数据错位）。

#### （2）建模的意义

1）实现数据的汇聚和集成，满足业务发展的差异化数据需求

2）实现数据分层和建模，提高数据的使用效率。使得数据结构清晰、数据指标统一、血缘关系清晰、快速定位数据异常、减少重复开发、屏蔽异常的原始数据和dwd层的细节。

3）数据持久化存储，有效地反映历史数据变化

#### （3）如何建模

##### 1）建模方法

**范式模型：**基于实体-关系建模**。**消除了数据不一致性、数据冗余度低，但是表格多指标的取数据需要多表关联效率低。下面是三范式规则：

**属性值的唯一性。**

**每张表中非主键必须完全依赖于主键，且只有一个主键。**

**每张表中，非主键属性只能依赖于主键，而不能依赖于表中的气他属性，否则应该单独传一张表，将该依赖关系轨道新表的关系中。**

**维度模型：**基于事实-维度建模。有星星模型、雪花模型、星座模型。建模规则如下：

**事实表（dwd层，某一业务过程或者主题主表 + 维表主键）由ods层数据清洗转换加密关联得来。**

**维表（dim层，某一业务相关的维度描述，如时间地点等信息），由ods主维表+相关维表关联得到。**

##### 2）建模分层

![5cac9b974615050e913d5522730cd13.jpg](assets/云层上的蓝天(乱)-13.jpeg)

##### 3）建模设计过程

**梳理业务流程**：把业务流程切分为多个关键流程（明确核心实体、事件、关系）

**确定事实表粒度**：如何描述事实表的一行数据(下单后一个订单的价格，还是下单后一件产品的价格)

**确定事实表维度**：与事实表核心实体相关的维度描述信息（时间，地点，人物等）

**确定事实表度量**：放款额、授信额、授信通过率等量词，注意区分是否可累加。

**退维**：将比较常用的维度信息退化关联到事实表中。让事实表结构清晰、冗余度较低、节省存储成本，减少后续计算关联次数。

##### 4）建模注意事项

数**据标准化不要只停留在数据部门**

**做好元数据的管理支持**

**做好数据质量监控体系**

**事实表设计注意事项**：尽可能包含所有业务过程相关的事实；事实的粒度和度量应保持一致

**预防维度爆炸**：尽量将次维表退化到主维表中。

**预防维度过渡退化**：过渡退化会使事实表太过于庞大冗余；过度违背范式规则；灵活性降低

**缓慢变化维处理**：保留数据原始值（每一次变化都是insert）；覆盖原始值（每次变化都是update）；拉链表保留历史状态，同时99999999分区保留最新数据便于后续计算。

kylin：和Hadoop的融合度高且支持SQL，是预计算模型，提前对海量数据进行聚合，然后构建索引来提升查询效率。适用于提前设置好维度和指标的场景。

##### 2）数据准备

变量结构化构建方法：

①明确算法需要的原始自变量X和因变量Y，遵循变量的粒度从粗到细，步步递进，结构清晰；②通过变量的4个要素进行组合，一个变量主要有四个要素成分，分别是变量的事实、变量参与主体的维度、时间窗口维度和对实时的度量。 ③应该校验变量的合理性和二义性。

明确变量口径

确定了X和Y的4个要素后，还需要明确X和Y的详细口径和计算方法。之后由数据开发工程师根据事前确定的定义、口径和计算方法从数仓中提取所需的X和Y的明细数据。

##### 3）数据预处理

数据校验：如命名合理性校验、清单和汇总值一致性校验、字段唯一性和一致性校验、缺失值校验、异常值校验、尺度一致性校验、格式校验、数据重复性校验、数据合理性校验、数据完整性校验。

数据清洗：解决校验阶段出现的问题数据。

##### 4）特征工程

特征衍生：衍生宏观经济指标等指标、衍生主题标签属性等指标、标志位补充、根据值的排序惊醒分组衍生新的变量、根据只的频率情况进行分组衍生新的变量、增加聚类标签、组合特征、把多个印字交叉分组、特征变换。

特征选择：对衍生出来的特征集合筛选适合的特征，选择方法如下，单变量分析、删除低方差特征、变量重要性排序、模型精度值变换、IV排序、计算现行相关性、业务专家选择

##### 5）模型构建

**模型分类：**

线性和非线性算法：线性的有回归、逻辑回归等；非线性的有决策树、梯度提升树、聚类算法、神经网络等。

监督和非监督学习方法

分类、聚类和回归算法

**单个模型：**如PageRank算法。原理为 初始化、计算转移矩阵P、计算调整矩阵T、迭代计算vt、计算的到图网络中节点的重要性权重矩阵vn。

**混合模型：**不同的算法模型适应不同的场景。线性算法的优点是简单、运行高效和解释性强，缺点是无法有效地模拟复杂的非线性关系，很多场景中性能比较一般。而非线性算法的优点是效果比较好，能被广泛应用于复杂的业务场景，缺点是复杂度高、计算量大、缺乏解释能力。混合建模对各个专家模型的要求有两个：各个专家模型的差异性越大越好、各个专家的模型性能不能差异太大。建模方法有:bagging法通过数据集的差异让同一个算法可以随机选择不同的数据行或者不同的数据列从而构建出多个差异化的模型、boosting法荣国修改训练数据的不同权重构建多个模型、stacking法师吧基础模型的结果作为新增的属性，将其与原始的特征合并在一起作为新模型的输入特征。

##### 6）模型评估

构建模型后，需要选择合适的模型进入生产环境（可能会设计模型调参）。

分类模型评估标准：将不同的因变量X对应的结果Y分到不同的类别中，常用的评估方法有，准确率检测法、捕获率和覆盖率检测法、F1值检测法、ROC曲线和AUC检测法、KS值检测法和Lift值检测法。

回归模型评估标准：将不同的因变量X对应的结果Y计算出来的过程中，常用评估方法有、R平方检测法、均方根误差法、平均绝对百分比误差法、模型的拟合度和区分度检测法等。

##### 7）模型部署

1.模型服务化流程：结局模型的持久化问题，让模型能够随时可用。

主要流程：完成模型的线上部署；输入特征部分来自离线数仓，部分来自实时的客户数据，需要对两者进行关联和聚合得到模型输入需要的字段；按照模型对输入特征的要求对输入数据进行合并和预处理，以获得标准化的输入特征；调用部署好的模型服务，得到模型的输出数据；根据模型的输出数据执行事前确定好的策略。

2.模型线上化部署：第一步是模型的存储和加载，第二部是实现模型的服务化。

3.算法即服务性能保障：数据中台的其他核心组件的性能以及算法本身的性能和计算时间复杂度也会影响算法即服务的综合性能。

##### 8）模型监控与迭代

要对模型的效果需要进行实时监控，也要对模型的输入进行监控。当发现模型的效果下降幅度超过预先设置的阈值时，我们应该及时对模型进行优化和迭代。

# flink on k8s 架构梳理

## 1.架构背后需求：

架构分块：

基于大屏报表实时性要求的提出，我们做了一套flink on k8s的实时数据流批一体处理架构。flink on k8s 作为计算及资源调度核心、docker+harbor存储镜像为streampark布置flinksql作业提供镜像的推拉存储服务，rancher实时监控k8s集群及集群作业运行状态，ajreport对实时计算结果以驾驶舱形式展示。

数据流向：

数据由flinkcdc从rds读取，在flink中开窗计算处理，处理结果通过kafka连接器写入datahub作为实时数仓分层供下一步继续处理，或者jdbc直接将最终结果层数据落库rds，再由ajreport书写数据集（sql）查询结果最终以驾驶舱形式展示。

## 1.flink on k8s：

### （1）flink：

#### 高吞吐低延迟：

**支持 Event Time 和乱序事件：**

Event time 使得计算乱序到达的事件或可能延迟到达的事件更加简单。

**状态计算的 exactly-once 语义：**

流程序可以在计算过程中维护自定义状态。Flink 的 checkpointing 机制保证了即时在故障发生下也能保障状态的 exactly once 语义。

**高度灵活的流式窗口：时间窗口（定时发车）、计数窗口（人满就走）**

streaming api：滚动、滑动、会话窗口

sql api：滚动、滑动、累计窗口，我们主要使用的是滚动窗口+窗口触发器，提前触发计算结果每5s输出

### （2）k8s：作为flink资源调度平台

集调度、资源管理、服务发现、健康检查、自动扩缩容、滚动升级…

### （3）streampark：

StreamPark 提供了一个流处理应用管理平台，核心能力包括但不限于应用开发、调试、交互查询、部署、运维、实时数仓等。flinksql作业由页面提交，与flink镜像重新构建新的镜像推送到k8s上运行，最终运行状态、日志等信息返回到streampark页面供我们监控作业。

### （4）flinkcdc、jdbc、kafka（datahub）。。。

flink的多种连接器，使得flink在与不同数据源读写交互更加方便

flinkcdc：

相比于canal+kafka，flink有以下优势

① 减少维护的组件、简化实现链路；  
② 减少端到端延迟；  
③ 减轻维护成本和开发成本；  
④ 支持 Exactly Once 的读取和计算（由于我们是账务系统，所以数据一致性非常重要）；

​  

## 2.容器化应用程序：

使用k8s必然少不了对于镜像的操作与存储，必然要使用docker技术。我们还使用harbor在内网作为私有镜像仓库。而作为生产级镜像存储需要高可用搭建，harbor需要依赖于postgresql（存储 Harbor 的应用数据，比如项目信息、用户与项目的关系、管理策略、配置信息、Artifact 的元数据等等）、redis(缓存服务器，用于存储生命周期较短的数据，例如镜像扫描工具clair、trivy、chartmuseum等以redis作为缓存，存储临时数据)、oss（镜像文件的存储）的高可用。我们部署了postgresql的高可用，并且搭配使用已有的redis和oss。

## 3.集群管理与监控

基于频繁使用k8s命令来管理集群，当集群众多的时候不方便管理及拍错信息查看。此时我们利用helm在独立的k8s集群上部署了rancher服务，用于将所有k8s集群注册到rancher服务，通过rancher 的ui界面实现点点点管理集群（创建或者注册新的k8s集群）/集群上的作业，以及作业日志的查看。

## 4.作业实践

目前我们这套系统刚上UAT，将之前航旅贷产品授信放款余额伪实时统计需求（小时批量代替实时）迁移到这套实时系统上来做，基于flinksql的窗口，我们可以利用累计窗口函数轻松将小时、天、月、年等时间段的指标统计变成实时结果更新展示到开源报表系统ajreport。
